# Índice de bloques de AUNEA Internal

**AUNEA Internal V2.0 REVIEW — CORE** (nunca `PRODUCTION`). Construida sobre el refactor UX/funcional V1 (Bloques A-L: Design System AUNEA con tokens exactos de `TOKENS_AUNEA`/`DESIGN_SYSTEM_AUNEA`, labels ES gobernados para enums de motor, procedencia "Tomado de: <origen>" sin fugas técnicas, modelo de completitud compuesto sin denominador fijo de 100 campos, CRM con pestañas/filtros/edición, reordenación de pasos, candidatos neutrales de integración DF054, pantalla de cierre real, limpieza de código muerto shadowed). V2.0 CORE añade: progressive disclosure en los editores de Process Step (6 grupos)/Fricción/Riesgo/Economics (3 pasos guiados: ámbito → cuantificación → valor económico), "Añadir varios pasos" distinto de "+ Crear nuevo paso como siguiente", ayuda contextual discreta (icono+popover) sobre `process_step_model`/`friction_model`, Modo Sesión reforzado (códigos técnicos nunca protagonistas, resueltos vía `REF_ACTION`/`REF_LEVEL_FUNC`/`REF_LEVEL_AI`), **PDF AUNEA real** (`aunea_backend/pdf_export.py`, reportlab, `application/pdf`, nunca recalcula reglas — DEC-041, sustituye `window.print()`), y un **sistema UAT reiniciado** exclusivamente Interno: Fase 1 carga un dataset CRM completo `UAT1-CRM-*` (12 empresas, 24 contactos, 24 interacciones, 16 oportunidades), con limpieza segura de datos UAT anteriores y sin crear Estudios/Projects; las UAT de Estudios quedan reservadas a Fase 2. Persistencia/recuperación y UAT visible están separadas en módulos distintos, y la captura de riesgo, economics y ciclo de vida AS-IS vive en `AUNEA-FE-RISK-CAPTURE-030` / `AUNEA-FE-ECON-CAPTURE-030` / `AUNEA-FE-PROC-LIFECYCLE-030`, fuera del Engine Adapter, que no genera UI de captura. El Template System canónico queda activado en runtime para Process y Step mediante plantillas estructurales que sólo INSTANTIATE_AS_DRAFT y conservan Template_ID/Version; Friction/Risk/Economic templates y gestión completa INT02 permanecen diferidos. Pain → Economics → Risk → Recommendation → Pricing → Scenario permanece server-owned en todo momento. Este índice cubre el runtime vigente completo (frontend + backend + build/launcher) y se audita automáticamente con `3_SYSTEM/frontend/tests/block-id-audit.test.cjs`. La promoción a `main` queda condicionada al gate automatizado vigente y al UAT visual/nativo final (Windows/Chrome/Edge), pendiente de ejecución manual por el usuario.
